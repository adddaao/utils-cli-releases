# Terminal#1-52 显示不全修复计划

## 现状确认（为什么还“不对”）
从当前代码链路看，主界面最终渲染使用了 `DocStyle.Margin(1,2)`，但布局计算在部分路径上仍可能按“终端原始尺寸”或“重复扣减/未扣减外边距”的方式计算，导致：
- 总渲染高度/宽度超过终端可视区域 → 底部被截断或触发终端滚动（用户看到“显示不全”）
- 左侧分隔线在部分行缺失、帮助栏第二行对不齐（用户看到“结构不对”）

本轮计划的核心目标是：让最终渲染的**可见字符网格**严格适配终端尺寸（不滚动、不截断），并确保左右列分隔线在每一行都连续存在。

## 目标（优化成什么、最终结果长什么样）
目标 UI（示意）：
```
┌─────────────┬─────────────────────────────────────────┐
│  > Docker   │  Docker 管理                            │
│    清理工具 │  （面包屑区域，固定 3 行）              │
│    Find     │  ─────────────────────────────          │
│    防火墙   │  （内容区，占满剩余高度）               │
│             │                                         │
│             ├─────────────────────────────────────────┤
│             │  ↑↓ 移动 • Enter 确认 • q 退出           │
│             │  Tab 切换到右侧内容区                    │
└─────────────┴─────────────────────────────────────────┘
```
硬性指标：
- 终端 80x24 下：界面不滚动、不截断
- 面包屑/内容/帮助栏在右侧列内对齐；帮助栏两行完整可见
- 左侧到右侧的竖分隔线在所有行连续存在（不出现缺口）
- 任意终端尺寸变化（拖拽缩放）时：界面实时自适应，不依赖固定宽高

## 实施步骤（按顺序，全部为动态计算）

### Step 1：彻底统一“可用尺寸”的来源与使用点（基于 WindowSizeMsg 动态更新）
目的：避免外边距在不同函数中被重复扣减或遗漏扣减。
- 在主布局（窗口尺寸更新、View 渲染）中，统一以 `CalculateAvailableSize(dims.Width, dims.Height)` 得到 `availableWidth/availableHeight`。
- 明确约束：后续所有“布局宽高拆分”都以 `availableWidth/availableHeight` 为输入，禁止再在拆分函数内部扣 `DocStyle` 外边距。
- 每次收到 `tea.WindowSizeMsg` 时 SHALL 重新计算 `availableWidth/availableHeight` 并向下游组件同步（content/list 等），确保拖拽缩放时实时生效。

产出：
- 主布局对“可用尺寸”的使用点统一（WindowSizeMsg 与 View 一致）。

### Step 2：修正高度拆分（保证总高度 = availableHeight）
目的：让右侧三块（面包屑/内容/帮助栏）相加恰好等于可用高度，并与 `DocStyle.Margin` 叠加后恰好等于终端高度。
- 重新校准三块高度是否包含边框行（面包屑下边框、帮助栏上边框）。
- 确认 `CalculateBreadcrumbHeight / CalculateHelpHeight` 与对应 style 的 Border 配置匹配（高度包含边框）。
- 确保内容区高度计算为：`availableHeight - breadcrumbHeight - helpHeight`（最小值保护可保留）。

产出：
- 80x24 下高度严格贴合，不溢出。

### Step 3：修正宽度拆分（保证总宽度 = availableWidth）
目的：避免“可用宽度”已经扣过左右外边距后，再次被拆分函数扣减导致右侧被挤压或错位。
- 将 `CalculateNavWidth/CalculateContentWidth` 的输入语义改为“可用宽度”，并移除函数内部对 `DocStyle.GetFrameSize()` 的扣减。
  - 或者：保留函数但主布局不再调用它（只在一个地方扣减外边距，且只扣一次）。
- 确保 `navWidth + contentWidth == availableWidth`。

产出：
- 右侧分隔线位置稳定、宽度不抖动。

### Step 3.5：清理“固定宽度字符串/分隔线”导致的自动换行（关键）
目的：解决你截图里右侧出现超长横线、或某些行自动换行导致高度被“偷偷增加”，最终表现为“显示不全”。
- 全局排查所有硬编码宽度/长度（例如固定 `strings.Repeat("─", 80)`、固定输入框宽度等）。
- 规则：任何一行输出的可见字符宽度 SHALL 不超过其所在列的宽度（`navWidth` 或 `contentWidth`）。
- 对分隔线/标题线：改为按当前可用宽度动态生成（例如 `repeat(contentWidth)`），禁止固定 80。
- 对过长文本（例如帮助栏、路径、状态行）：使用截断/省略策略，确保不触发终端自动换行。

产出：
- 任意窗口尺寸下不会因为“某一行太长”而额外换行；整体高度保持可控。

### Step 4：保证竖分隔线全高连续（修复你截图里的“缺口/对不齐”）
目的：解决左侧竖线在帮助栏第二行缺失、行首对不齐的问题。
- 放弃依赖“导航栏右边框”来充当整屏分隔线的方式，改为显式渲染一个“分隔线列”：
  - 使用可用高度生成一个固定宽度为 1 的列（每行一个 `│`），颜色与当前主题一致。
  - 以 `JoinHorizontal` 拼接：`导航列 + 分隔线列 + 右侧列`。
- 这样分隔线与导航内容解耦，即使导航渲染的行数或 padding 变化，分隔线也不会断。

产出：
- 分隔线每一行都存在；帮助栏两行左侧均有 `│` 对齐。

### Step 5：帮助栏渲染一致性校验（修复 “•   •” 这种异常间隔）
目的：确保帮助栏 items 序列没有空项导致多余分隔符，并确保多行内容不发生错列。
- 检查帮助栏数据来源（设置两行 help items 时）是否可能插入空项。
- 在帮助栏渲染中对 Key/Desc 为空的项做过滤（避免生成“空项 + 分隔符”）。
- 确保每一行帮助文本的宽度被约束在右侧列宽度内（必要时做 padding/截断）。

产出：
- 帮助栏渲染无“空分隔符”、两行对齐不跑偏。

## 验证方式（必须通过，验证点为动态适配而非固定尺寸）
### 1）自动化验证（推荐）
- 增加一个轻量测试：构造 `MainLayoutModel`，发送 `tea.WindowSizeMsg{Width:80,Height:24}`，调用 `View()`：
  - 去除 ANSI 序列后，验证渲染结果行数 **等于 24**；
  - 验证每行可见宽度不超过 80；
  - 验证竖分隔线列在所有行存在（例如固定列位置字符为 `│`）。

### 2）人工验证（终端实测）
- 80x24：不滚动、不截断；底部帮助两行完整可见
- 100x30、120x40：布局稳定，分隔线连续
- 任意拖拽缩放：界面实时重排，无滚动抖动、无“突然少一截”

- `internal/tui/style.go`：统一宽度拆分函数语义（输入为可用宽度）；校准高度常量与边框匹配
- `internal/tui/help_bar.go`：过滤空 help item；保障多行渲染对齐
- （可选）新增 `internal/tui/layout_test.go`：终端尺寸适配的回归测试
