# 新功能编写规定

本文档用于约束 `ru` 后续新增功能的设计、实现、交互、打包和验收。当前迭代默认允许破坏性更新；除非明确提出兼容要求，不为旧行为、旧配置或旧发布结构额外做兼容迁移。

## 基本原则

1. 新功能必须先复用现有架构和组件，不新增平行框架。
2. 业务能力优先放在对应领域包内，TUI 只负责状态编排、展示和快捷键交互。
3. 新增状态必须可解释、可回退、可测试，不能只靠临时字符串或隐式布尔值驱动流程。
4. 所有用户可见文案、文档、配置示例和错误提示必须使用中文。
5. 涉及删除、清理、覆盖旧文件的行为必须走废纸篓语义，禁止使用硬删除。

## TUI 功能规定

TUI 的目录分层、内容展示、公共组件、帮助栏、流程面包屑、执行任务日志、编号选择和列表导航等核心规则，请严格遵循项目根目录的 `AGENTS.md`（或 `CLAUDE.md`）。为避免规则漂移，本文档不再重复维护具体的 TUI 约束条款。

## 清理与删除规定

1. 任何删除文件、目录、构建产物、临时文件的行为都必须使用 `trash` 能力。
2. Go 代码内必须走 `internal/trash`，脚本中必须调用 `trash` 命令。
3. 禁止新增 `rm`、`rm -rf`、`os.Remove`、`os.RemoveAll`、`Remove-Item` 等硬删除路径。
4. 删除失败必须返回明确错误，不能降级为硬删除。
5. 清理模板必须先完成规则、路径、关键路径保护校验后才能执行。

## 配置与模板规定

1. 配置结构可以破坏性更新，但必须同步更新默认配置和示例配置。
2. 新增配置字段必须有清晰命名、中文说明和合理默认值。
3. 模板不是规则集合的别名，模板必须是完整执行流程配置，包括名称、规则、路径、动作和安全校验结果。
4. 禁用模板、未知规则、空规则、关键路径模板必须不可执行。
5. 手动流程和模板流程必须共用底层规则能力，不复制规则语义。
6. 清理模块内置模板只能由程序代码提供；用户模板必须保存在主配置同目录的 `clean_templates.toml`，不允许继续写入主 `config.toml` 的 `clean.templates`。

## 打包与安装规定

1. `ru` 和 `trash` 是两个独立程序。
2. 每个平台发布包必须包含当前平台的 `ru` 与当前平台的 `trash`。
3. 不同平台的 `trash` 不得混放到同一个安装结果中。
4. 安装时只复制当前平台需要的 `ru` 和 `trash`，并统一放入 `ru` 安装目录；Linux/macOS 为 `~/.local/share/ru`，Windows 为 `%LOCALAPPDATA%\Programs\ru`。Unix 安装不得要求或支持 `sudo`。
5. 发布脚本缺少目标平台 `trash` 产物 URL 时必须失败，不允许生成不完整发布包。

## 测试要求

新增功能至少满足以下验证：

1. 涉及 TUI 布局时，必须覆盖 `80x24`、`100x30`、`120x40` 等尺寸。
2. 涉及快捷键时，必须测试“帮助栏声明”和“实际可用行为”一致。
3. 涉及面包屑时，必须测试当前状态对应的流程节点正确，且不得回退到默认模块名、`当前任务` 或泛化占位。
4. 涉及流程跳转时，必须测试任务完成后的目标状态正确，尤其是不同功能返回相同数据类型时不能乱跳。
5. 涉及删除或清理时，必须测试关键路径保护和废纸篓调用路径。
6. 涉及打包脚本时，必须至少执行脚本语法检查。
7. 常规回归命令：

```bash
make test
make build-mac        # 其他宿主平台改用 make build-linux / make build-windows
git diff --check
```

## 代码审查清单

提交新功能前必须自查：

1. 是否新增了隐藏快捷键。
2. 是否有未进入帮助栏的可触发操作。
3. 是否有硬删除残留。
4. 是否会在小窗口下换行撑破布局。
5. 是否把并行入口误画成线性流程。
6. 是否复制了业务状态机而不是复用现有能力。
7. 是否更新了中文文档、配置示例和测试。
8. 是否有状态落到默认面包屑、`当前任务` 或泛化占位。
9. 是否验证了新增流程不会跳到其他功能或旧状态。
10. 是否仍有手写冒号对齐、缩进拼接或按钮字符串形式的手动表单。
